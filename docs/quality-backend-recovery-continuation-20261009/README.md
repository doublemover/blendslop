# Backend OBJ ownership and recovery inspection

This successor change gives the visual-hull mesh OBJ producer a fresh owned stage and publishes its final file atomically without overwriting prior files. Recovery inspection reports what existing ownership records support; it never releases a lease or executes recovery or reclamation.

## Production scope and compatibility

`reconstruction/backend_artifact_ownership.py::write_owned_backend_obj` wraps the existing `mesh_io.write_obj` serialization. `reconstruction/backends/visual_hull/artifacts.py::write_visual_hull_mesh_artifact` is the one connected producer. Its backend caller already consumes the returned mesh path for `mesh_artifact_export.path`; exported/skipped/failed metric semantics and OBJ encoding remain unchanged.

A successful first export keeps the default `m/vh.obj`. An occupied final chooses `vh_2.obj`, then subsequent suffixes, with at most 128 atomic publication attempts. Returned relative paths stay relative. Publication uses the existing `os.link` utility, which requires a compatible filesystem and retains the complete stage. It does not copy, delete or replace an existing final. Unsupported hard links remain a reported export failure rather than falling back to overwrite.

Each export creates only a fresh `m/.export-runs/owned-*` directory. The complete or partial `mesh.obj`, `export-result.json`, manifest and lease remain retained. A new `mesh_export_ownership` artifact points to the export receipt before writing begins, so the existing backend export-failure path retains a reachable receipt. The manifest records the actual final path, size and SHA256 after publication, including when the later result receipt fails. A receipt error does not replace an earlier writer/publication exception.

The generated byte allowance is a generous encoding estimate checked before writing and against actual registered bytes; it is not an operating-system disk quota or a process memory limit. This synchronous exporter starts no subprocesses. It releases only its own lease after serialization/publication finishes. Volume/NPZ/OpenVDB files, editable-proxy JSON, candidate roots, caches, artist files, inputs and all other backend/export producers remain outside this adoption. The final is an external published file; recording its binding does not adopt historical files. A later edit through either hard link causes the ownership audit to detect content drift.

## Read-only recovery interface

`utils/run_recovery.py::inspect_run_recovery` requires an explicit run ID and owner token. It refuses missing/unowned folders, redirected roots, mismatched identity, oversized control records and stale expected snapshots. Its metadata limits are 1 MiB per manifest, 64 KiB per lease and 4,096 registered artifact entries. Released-run verification reuses the existing bounded reclamation planner (default 256 MiB total hashed artifact bytes). The inspector re-reads both control files and rejects changes during inspection. A snapshot binds exact manifest/lease bytes; it is not a durable lock or permission for a later mutation.

| Existing state | Decision | Meaning |
| --- | --- | --- |
| Active lease, including a crashed producer | `retain_active_lease` | Original process start identity and complete descendant join evidence are unavailable. |
| Released lease with verified records | `no_recovery_needed` | Ownership audit passed; no recovery or cleanup executes. |
| Released lease with drift, unknown files or verification limits | `retain_unverified_released_run` | Preserve the run and report audit blockers. |
| Missing, malformed, mismatched or changing records | `refuse_unverifiable_ownership` | Inspection does not establish a bound decision. |

`process_identity_verified`, `descendant_joins_verified`, `lease_release_supported` and `recovery_execution_supported` remain false. Active inspection does not claim registered-artifact verification. The real crash fixture waits for its child and observes exit code 17, but that separate test fact cannot establish original process identity or a complete descendant inventory in the existing manifests. No PID disappearance, caller boolean or fabricated join proof is accepted. An actual crash-recovery executor remains blocked on a supervisor-bound original process identity, complete ownership-bound descendant records and joins, and a separate explicit history-preserving recovery decision. No shared `run_ownership.py` changes or deletion mechanism were introduced.
